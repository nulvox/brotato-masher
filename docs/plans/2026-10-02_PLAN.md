## Objective
Create a locally runnable, GitHub Pages-compatible Brotato save editor inspired by the user-provided `nulvox/sleditor` example, using the installed save as the format reference. The editor will use a Go core compiled to WebAssembly for save parsing, validation, controlled mutation, and serialization, plus a thin JavaScript wrapper for browser File/Blob APIs and DOM delivery. It must import a user-selected JSON save in the browser, expose safe common edits, preserve the rest of the save, and export a downloadable JSON file without any server or runtime network dependency.

## Track
Track: Standard — greenfield browser tool with a game-save trust boundary, format uncertainty, and multiple deterministic validation paths.

## Scope
### In scope
- Repository `flake.nix` dev environment for Go/WASM, JavaScript tooling, Chromium, and browser automation. The exact browser automation package must be verified against nixpkgs during implementation; Chromium headless is the bounded fallback.
- Go package/core compiled with `GOOS=js GOARCH=wasm`.
- Thin JavaScript wrapper limited to DOM events, File/Blob APIs, `wasm_exec.js` bootstrapping, and download delivery.
- File picker plus drag/drop or text fallback for importing a Brotato `save_v3_0.json`.
- Structural validation of JSON and required/recognized Brotato v3 fields; clear errors for malformed or unsupported input.
- Dashboard for the detected save version and collection counts.
- Editing the known unlock collections (`characters_unlocked`, `consumables_unlocked`, `items_unlocked`, `upgrades_unlocked`, `weapons_unlocked`, `zones_unlocked`) with safe select-all/clear controls and numeric ID presentation.
- Editing numeric lifetime statistics under `data` with bounded non-negative integer inputs.
- Optional whole-save unlock-all action only if implemented as an explicit, reversible in-memory operation; preserve unknown fields.
- Download of a validated, pretty-printed JSON save; never overwrite the source file automatically.
- Backup/export warning and concise instructions for locating/replacing the Steam save.
- GitHub Actions Pages deployment using the official Pages artifact/deployment actions, triggered on pushes to the default branch, with a separate pull-request build/test job.
- GitHub Pages deployment documentation and deterministic Go plus browser validation.

### Out of scope
- Direct filesystem writes to the Steam save, Steam Cloud integration, or server-side upload/storage.
- Network calls, analytics, accounts, or telemetry.
- Reverse engineering the binary game package for human-readable item/character names in the MVP.
- Editing active run state, difficulty completion semantics, or arbitrary unknown JSON fields via bespoke controls.
- Copying source/code/assets from the external exemplar; only high-level interaction patterns may inform the design.

## Execution Strategy
1. On approval, create and enter the repository Nix dev shell; verify the requested Go/WASM and browser automation toolchain before coding.
2. Establish the Go format contract and fixture tests; use the observed save as a local reference but do not copy the personal save into the repository.
3. Build the Go WASM core, then the minimal JS wrapper and accessible static shell.
4. Add the GitHub Actions Pages pipeline: checkout, enter Nix environment, run Go/WASM/browser tests, build `dist/`, upload Pages artifact, and deploy on the configured default branch; pull requests run build/tests without deployment.
5. Keep the editor entirely client-side: file picker -> JS passes text to WASM -> Go validates/clones/mutates/serializes -> JS creates Blob download.
6. Validate malformed/unsupported inputs before enabling export, and never expose raw save contents in logs or URLs.
7. Run Go tests, WASM artifact checks, Playwright smoke tests, static HTTP checks, and workflow assertions; use Chromium fallback only if Playwright cannot be provided by the flake.
8. Review against every acceptance criterion, including source preservation, no runtime network calls, accessibility basics, WASM loading, and GitHub Pages compatibility.

## Risks and Mitigations
- **Save corruption / loss:** never overwrite; preserve unknown keys; validate output; require backup instructions.
- **Game updates changing schema:** version gate and explicit unsupported-version message; keep mutations narrow.
- **Incorrect unlock semantics:** edit arrays and counters conservatively; do not invent difficulty/run-state data.
- **Privacy exposure:** no upload/server/analytics; do not commit the personal save.
- **ID usability:** clearly label raw numeric IDs and defer guessed names.
- **Browser compatibility:** use widely supported File/Blob/DOM APIs and a small JS wrapper; verify WASM loading in Chromium.
- **WASM bridge complexity:** keep the exported JS API narrow and test it through browser smoke tests; do not expose arbitrary Go internals.
- **Nix package availability:** verify Playwright package names and browser-driver compatibility in the flake; retain Chromium headless as a documented fallback rather than installing globally.
- **Pages configuration drift:** keep build and deployment in one reviewed workflow and test pull requests without deployment.
